# 15. MultiThreadedRendering — 이건 어떻게 만들었을까?

1단계부터 지금까지, 그림 그리는 코드는 항상 커맨드 리스트 하나에 순서대로 명령을
쌓기만 했어요. CPU 입장에서는 "이거 그려, 저거 그려, 다음엔 이거 그려..."를 한
줄씩 순서대로 적어 내려가는 거라, 오브젝트가 아주 많아지면 이 "적어 내려가는"
작업 자체가 CPU 시간을 꽤 잡아먹어요. 이번 단계는 그 "적어 내려가는" 작업을 여러
CPU 스레드에 나눠서 동시에 하게 만들어봐요.

## 1. 무엇을 나눌까?

지금까지는 큐브가 딱 1개였어요. 여러 스레드로 나눠서 기록할 만큼 일이 많지
않았죠. 그래서 이번 단계는 먼저 큐브를 4x4 그리드, 총 16개로 늘렸어요. 16개면
"이 중 4개는 스레드 A가, 다른 4개는 스레드 B가..." 식으로 나눌 이유가 생겨요.

## 2. 커맨드 리스트는 왜 스레드마다 따로 필요할까?

`ID3D12GraphicsCommandList`에 명령을 기록하는 건 그 리스트 하나만 건드리는
작업이라 여러 스레드가 **서로 다른** 커맨드 리스트에 쓰는 건 자유롭게 동시에 할 수
있어요. 하지만 같은 리스트 하나에 여러 스레드가 동시에 쓰면 순서가 뒤죽박죽
꼬여버려요. 그래서 워커 스레드 개수(`WorkerThreadCount` = 4)만큼 커맨드
얼로케이터/리스트 쌍을 미리 만들어두고, 스레드마다 자기 것만 건드리게 했어요.

## 3. 커맨드 리스트는 서로 상태를 기억하지 못해요

여기서 초보자가 자주 놓치는 부분이 하나 있어요: 커맨드 리스트 A에서
"렌더타깃은 이거야", "파이프라인은 이거 써"라고 설정해놓아도, 그 다음에 실행되는
커맨드 리스트 B는 그걸 전혀 몰라요. `ExecuteCommandLists`로 A, B를 순서대로 같이
제출해도 마찬가지예요 - 각 커맨드 리스트는 자기가 기록될 때 필요한 상태(렌더타깃,
뷰포트, 루트 시그니처, 파이프라인 상태, 디스크립터 힙)를 전부 자기 안에 직접
기록해둬야 해요.

그래서 `RecordWorkerCommandList`를 보면, 메인 커맨드 리스트가 이미 똑같은 설정을
해놓았는데도 워커 스레드마다 렌더타깃/뷰포트/루트 시그니처/PSO/디스크립터 힙을
처음부터 다시 설정해요. 중복처럼 보이지만, 커맨드 리스트가 독립적으로 동작하기
위한 필수 규칙이에요.

## 4. 실제 흐름

</p>

1. **메인 스레드**가 그림자맵 패스(큐브 16개 + 바닥의 깊이만 그리기)와, 색상
   패스의 클리어 + 스카이박스 + 바닥 그리기까지 기록하고 커맨드 리스트를
   닫아요(`Close`). 큐브 16개의 "색"을 그리는 부분은 아직 아무도 기록하지
   않았어요.
2. **워커 스레드 4개**를 띄워요(`std::thread`). 스레드 0은 큐브 0~3번, 스레드
   1은 4~7번... 이렇게 4개씩 나눠 맡아요. 넷 다 동시에 자기 커맨드 리스트에
   그리기 명령을 기록해요 - 서로 다른 리스트라서 락(lock) 없이도 안전해요.
3. **메인 스레드가 기다려요**(`join()`). 넷 다 다 기록을 끝낼 때까지는 다음
   단계로 못 넘어가요.
4. **후처리 커맨드 리스트**에 리졸브 → 블룸 → 톤매핑 → 백버퍼 복사를 기록해요
   (12단계부터 그대로).
5. **한 번에 제출**: [메인 리스트, 워커 리스트 4개, 후처리 리스트] 순서로 배열에
   담아 `ExecuteCommandLists` 딱 한 번 호출해요. GPU는 이 배열 순서 그대로,
   마치 하나의 긴 커맨드 리스트였던 것처럼 차례로 실행해요.

## 5. 순서가 왜 안 꼬일까?

"여러 스레드가 동시에 기록했는데 GPU에서 순서가 안 꼬이나요?"라는 의문이 들 수
있어요. 답은: **기록은 병렬, 제출은 순서대로**예요. CPU가 명령을 적어 내려가는
작업(레코딩)만 여러 스레드가 나눠서 동시에 했을 뿐, GPU에 실제로 넘기는 시점
(`ExecuteCommandLists`)에는 항상 메인 스레드가 정해준 배열 순서대로 한 번에
제출돼요. 그리고 같은 커맨드 큐에 제출된 커맨드 리스트들은 배열에 적힌 순서
그대로 GPU에서 실행되니까, "바닥/스카이박스를 먼저 그리고, 그다음에 큐브 16개를
그리고, 그다음에 후처리한다"는 순서가 그대로 지켜져요.

## 6. 등장인물 소개

| 용어 | 비유 |
|---|---|
| 워커 스레드 (Worker Thread) | 큐브 몇 개씩 맡아서 각자 자기 노트(커맨드 리스트)에 적는 사람들 |
| 커맨드 리스트 (Command List) | 각 워커가 쓰는 자기만의 노트. 다른 사람 노트는 못 보고 못 씀 |
| `join()` | "다들 다 적었어?" 하고 메인 스레드가 전원 확인할 때까지 기다리는 것 |
| `ExecuteCommandLists` | 노트들을 순서대로 모아서 선생님(GPU)한테 한 번에 제출하는 것 |
| CubesPerWorker | 워커 한 명이 맡는 큐브 개수 (16개 ÷ 4명 = 4개씩) |

## 7. 결과 화면에서 확인할 수 있는 것

큐브가 1개에서 4x4 그리드 16개로 늘어났고, 각자 조금씩 다른 위상으로 회전하고
있어요. 그림자, 블룸, 톤매핑은 이전 단계와 똑같이 정상 동작해요 - 달라진 건 눈에
보이는 결과가 아니라, 그 16개 큐브의 그리기 명령을 CPU가 어떻게 기록했는가예요
(스레드 1개가 순서대로 vs. 스레드 4개가 동시에).

## 8. 요약 한 줄

> "커맨드 리스트에 그림 그리는 명령을 적는 작업을, 오브젝트 그룹별로 나눠서 여러
> 스레드가 동시에 하고, 다 끝나면 메인 스레드가 정해진 순서대로 한 번에 GPU에
> 제출한" 프로그램.
